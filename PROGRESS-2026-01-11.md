## Key Decisions Made

### 1. **Framework Migration: Mojo::Base → Moo::Role**
**Decision:** Migrate all required roles from Mojo::Base to Moo::Role to work with Thunderhorse framework.

**Rationale:**
- The Generals controller uses Mooish::Base (new Thunderhorse framework)
- The Pairs controller still uses Mojo::Base (old Mojolicious framework - not yet migrated)
- Roles using Mojo::Base cannot be composed with Mooish::Base controllers
- Therefore, we must migrate roles as we need them

**Roles Migrated:**
1. `Game::EvonyTKR::Controller::Role::Tables` (SSE streaming helpers)
2. `Game::EvonyTKR::Controller::Role::Generals::Routing` (route validation)
3. `Game::EvonyTKR::Role::Constants::BuffConstants` (buff/activation constants)
4. `Game::EvonyTKR::Role::Constants::GeneralConstants` (already Moo::Role)

**Migration Pattern:**
```perl
# OLD (Mojo::Base):
use Mojo::Base -role, -signatures;
has attribute => sub { default_value };

# NEW (Moo::Role):
use Moo::Role;
has attribute => (
  is      => 'ro',
  default => sub { default_value },
);
```

### 2. **Template System: .html.ep → .tt**
**Decision:** Use Template Toolkit (.tt) format instead of Embedded Perl (.html.ep).

**Rationale:**
- All existing Thunderhorse controllers use Template Toolkit (.tt files)
- Embedded Perl (.html.ep) is Mojolicious-specific and not supported by Thunderhorse
- The GeneralTableSingle.html.ep template was from the old Mojolicious implementation

**Templates Created/Converted:**
- `templates/generals/GeneralTableSingle.tt`
- `templates/generals/troopTypeIndex.tt`
- `templates/generals/activationIndex.tt`

**Template Toolkit Syntax:**
```tt
[% WRAPPER layouts/default.tt %]
  <h1>[% variable %]</h1>
  [% FOREACH item IN items -%]
    [% item.name %]
  [% END -%]
[% END %]
```

### 3. **Route Conflict Resolution: Static Routes First**
**Decision:** Register static troop type routes BEFORE the dynamic `:name` route.

**Problem:**
- Route: `/Generals/:name` (dynamic)
- Route: `/Generals/:troopType` (dynamic)
- Both patterns match the same URL structure
- Created routing conflict where `/Generals/cavalry-specialists` couldn't distinguish between general name vs troop type

**Solution:**
- Loop over `%generalKeys` hash and register static routes for each troop type
- Register these BEFORE the dynamic `:name` route
- Router checks static routes first, falls back to dynamic routes

**Implementation:**
```perl
# Register static routes FIRST (lines 76-95 in Generals.pm)
foreach my $generalType (keys %Game::EvonyTKR::Role::Constants::GeneralConstants::generalKeys) {
  my $ui_target = $self->_ui_target_name($generalType);
  my $slug = $self->_slugify($ui_target);
  $self->router->add("$base/$slug", { ... });
}

# THEN register dynamic route (lines 97-106)
$self->router->add("$base/:name", { ... });
```

### 4. **Route Validation: try_lookup_route() instead of lookup_route()**
**Decision:** Use `try_lookup_route()` which returns undef, instead of `lookup_route()` which croaks.

**Rationale:**
- `lookup_route()` calls `croak()` on invalid routes (causes Internal Server Error)
- In Thunderhorse, we should handle errors gracefully and return proper HTTP error responses
- Controllers should check for undef and call `render_error()` with appropriate status codes

**Change Made:**
```perl
# OLD:
my $route_meta = $self->lookup_route($uiTarget, $buffActivation);

# NEW:
my $route_meta = $self->try_lookup_route($uiTarget, $buffActivation);
unless ($route_meta) {
  return $self->render_error($ctx, 404, "Invalid general type or buff activation");
}
```

## Current Issue: validRoutes Not Populated

### Problem Description

The `validRoutes` attribute in the Routing role is not being populated when accessed by `try_lookup_route()`. This causes the catalog endpoint and activation index to fail with Internal Server Error.

### Root Cause Analysis

**The `validRoutes` Attribute:**
```perl
# In Game::EvonyTKR::Controller::Role::Generals::Routing (lines 15-26)
has validRoutes => (
  is      => 'ro',
  lazy    => 1,
  default => sub ($self) {
    unless ($vr) {
      $vr = {};
      $vr = $self->get_valid_routes();
    }
    return $vr;
  },
);
```

**The `get_valid_routes()` Method:**
```perl
# Lines 114-144 in Routing.pm
sub get_valid_routes($c) {
  foreach my $buffActivation ($c->AllowedBuffActivationValues->@*) {
    foreach my $tt ($c->GeneralKeys->@*) {
      # Filter combinations based on rules
      # Generate slugs
      # Save to $c->validRoutes hash
    }
  }
  return $c->validRoutes;
}
```

**Dependencies:**
- `AllowedBuffActivationValues` (from BuffConstants role)
- `GeneralKeys` (from GeneralConstants role)
- Both roles must be composed before `get_valid_routes()` runs

### Why Some Routes Work and Others Don't

**Working Routes:**
- `singleTable()` - Might be accessing `validRoutes` after it's been initialized by another call
- `troopTypeIndex()` - Doesn't call route validation at all

**Failing Routes:**
- `singleCatalog()` - Calls `try_lookup_route()` which accesses `validRoutes`
- `activationIndex()` - Calls `try_lookup_route()` which accesses `validRoutes`

**Hypothesis:**
The lazy initialization of `validRoutes` might not be triggering correctly, or `get_valid_routes()` is being called before the constants are available.

## Important Code Patterns

### SSE Streaming Pattern (from Tables role)

```perl
# Setup SSE headers
$self->setup_sse_headers();
$ctx->render_later;
$self->write_sse($ctx);
$ctx->inactivity_timeout(1200);

# Batch processing
my $batch_size = 50;
my $loop_delay = $self->table_loop_delay // 0.01;

my $process_batch = sub {
  # Process batch
  foreach my $item (@batch) {
    my $result = compute($item);
    $self->write_table_sse('row', $result);
  }

  # Check if complete
  if ($complete) {
    $self->send_complete_event($run_id, $total, 'items');
  }
};

# Execute first batch immediately
$process_batch->();

# Schedule remaining batches
my $recurring_id = Mojo::IOLoop->recurring($loop_delay => $process_batch);

# Cleanup on disconnect
$ctx->on(finish => sub {
  Mojo::IOLoop->remove($recurring_id);
});
```

**Problem:** `bin/server2.pl` was calling `Game::EvonyTKR->getConfig()` as a class method, but `getConfig()` is an instance method in WebFramework::App.

**Fix:** Added `$self->load_module('^WebFramework::Module::Navigation')` in `Game::EvonyTKR->build()` before loading controllers.

**Problem:** Templates expect `site_logo` variable, but no SiteLogo module was loaded.

**Fix:** Added `site_logo()` method to `ControllerBase.pm` that returns empty string (no logo configured for this project).

**Problem:** `activationIndex()` was calling `$ctx->redirect()` but redirects in Thunderhorse/PAGI use `$ctx->res->redirect()`.

**Fix:** Changed line 832 from `$ctx->redirect(...)` to `$ctx->res->redirect(...)`.

### 5. Catalog Endpoint Missing `async` Keyword
**Problem:** `singleCatalog()` uses `await` for `$ctx->req->json` and `$ctx->res->json()`, but wasn't declared as `async sub`.

**Fix:**
- Added `use Future::AsyncAwait;` to imports
- Changed `sub singleCatalog` to `async sub singleCatalog`
- Added `await` to `$ctx->req->json` call
- Changed `$self->render_json($ctx, ...)` to `await $ctx->res->json(...)`

### 6. Catalog Returns Empty Due to Wrong Filter Logic
**Problem:** `singleCatalog()` was filtering generals by `$general->type`, but the General model's `type` field is never set (not in YAML files).

**Fix:** Updated filter logic to use specialties instead of type:
- Map `generalType` (e.g., `mounted_specialist`) to troop type string (e.g., `Mounted Troops`) using `%GeneralTypes2TroopTypes`
- Filter generals whose `specialtyNames` contain references to that troop type
- For 'ALL' types (mayor, officer, wall), include all generals

# Update: January 16, 2026

## Issue Fixed: PostgreSQL Connection Error for Table Sessions

### Problem
When accessing the single general table routes, the server threw a PostgreSQL connection error:
```
connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: No such file or directory
```

This occurred because `Game::EvonyTKR::Role::Persistence::TableSessions` was delegating to `$self->persistence->store_table_session()`, which used PostgreSQL via the `Game::EvonyTKR::Service::Persistence` backend.

### Solution
Converted `TableSessions.pm` from PostgreSQL persistence to in-memory storage using a package-level hash. This is appropriate for Thunderhorse because:
1. Table sessions are ephemeral (1-hour TTL)
2. They don't need to survive server restarts
3. Thunderhorse runs as a single process, so in-memory storage is sufficient

### Changes Made

**File:** `lib/Game/EvonyTKR/Role/Persistence/TableSessions.pm`

1. Removed dependency on `Game::EvonyTKR::Role::Persistence::Core`
2. Added package-level hash: `our %SESSION_STORE;`
3. Rewrote all methods to use in-memory storage:
   - `store_table_session()` - Stores session in `%SESSION_STORE` with TTL
   - `get_table_session()` - Retrieves from hash, checks expiration
   - `expire_table_sessions()` - Removes expired sessions
   - `delete_table_session()` - Removes specific session
